1. Resumo Executivo

O ambiente foi disponibilizado com falhas controladas que impediam a renderização dos dados na interface do usuário. Embora todos os serviços da máquina estivessem com o status active (running), a comunicação inter-camadas estava bloqueada.

Diferença crucial entre Sintoma e Causa Raiz:

  • Sintoma percebido: A tela inicial exibia a mensagem de erro "Não foi possível consultar o banco" e a lista de itens não carregava.
  • Causas raízes reais: Foram identificadas e tratadas 3 anomalias interdependentes: falha de autenticação por senha arbitrária na API, ausência de privilégios ACL na tabela do PostgreSQL e cache estático de configuração pendente no Nginx.

2. Mapa da Arquitetura e Diagnóstico das Camadas

Camada 1: Web / Proxy Resolvido

Nginx 1.24 (Porta 80)

• Papel: Entrega do Front-end (HTML/JS) e roteamento de /api/*.

• Incidente: Requisições para /api/items retornavam HTTP 404.

• Causa: Processo em execução estava sem o reload da diretiva de proxy.

Ação: sudo systemctl reload nginx
Camada 2: Aplicação API Resolvido

Node.js / training-api (Porta 3000)

• Papel: Regra de negócio, consulta via psql e JSON REST.

• Incidente: HTTP 500 no endpoint /api/items.

• Causa: Systemd configurado com DB_PASSWORD=senha-incorreta.

Ação: Redefinição de senha & sync no systemd
Camada 3: Banco de Dados Resolvido

PostgreSQL 16 (Porta 5432)

• Papel: Armazenamento persistente (banco training).

• Incidente: Erro permission denied for table items.

• Causa: Role training_app não detinha concessão de SELECT.

Ação: GRANT SELECT ON items TO training_app

3. Matriz Técnica dos Incidentes & Intervenções

Incidente #1: Autenticação Rejeitada entre API e Banco de Dados

Camada API → DB

Ao inspecionar a unidade do serviço systemd em /etc/systemd/system/training-api.service, identificou-se a variável estática DB_PASSWORD=senha-incorreta. Como a senha cifrada no catálogo do Postgres utilizava algoritmo irreversível (SCRAM-SHA-256), a intervenção segura consistiu em padronizar a credencial em ambos os lados.

# 1. Redefinir credencial no PostgreSQL e sincronizar unit file:

sudo -u postgres psql -c "ALTER USER training_app WITH PASSWORD 'training2026';"

sudo sed -i 's/DB_PASSWORD=senha-incorreta/DB_PASSWORD=training2026/' /etc/systemd/system/training-api.service

sudo systemctl daemon-reload && sudo systemctl restart training-api.service

Incidente #2: Violação de Permissões ACL na Tabela do Banco

Camada DB

Com a senha corrigida, a consulta da API retornou o erro interno: detail: "ERROR: permission denied for table items". A tabela foi instanciada com propriedade exclusiva do superusuário postgres, bloqueando qualquer consulta da aplicação training_app.

# 2. Conceder permissão de leitura sobre a entidade:

sudo -u postgres psql -d training -c "GRANT SELECT ON items TO training_app;"

Incidente #3: Falha de Roteamento no Proxy Reverso (Nginx)

Camada Web

Embora a API respondesse diretamente em http://127.0.0.1:3000/api/items, as requisições de navegadores externos via porta 80 recebiam HTTP 404. O processo mestre do Nginx estava em execução contínua sem ter assimilado o bloco location /api/ definido no virtual host /etc/nginx/sites-available/training.

# 3. Teste de sintaxe seguro e recarga a quente sem perda de sessões:

sudo nginx -t

sudo systemctl reload nginx

5. Competências e Conclusão Técnica

✓ Raciocínio em Camadas & Diagnóstico Metódico

A resolução demonstrou que nem toda falha decorre de processos inativos ou quedas de serviço. O isolamento de cada camada (Web, API e Banco) com ferramentas objetivas (ss, curl, journalctl, psql) evitou alterações desnecessárias e permitiu intervenções precisas sem impacto colateral.

✓ Boas Práticas Operacionais

As ações corretivas respeitaram os princípios de menor privilégio (concessão de SELECT estritamente à tabela necessária) e disponibilidade de serviço (uso de systemctl reload no Nginx em vez de reinicializações abruptas que derrubariam tráfego).
